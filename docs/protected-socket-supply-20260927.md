# On-demand protected socket supply (2026-09-27)

The production management, signal and opt-in relay connectors use per-dial protected sockets. Management and signal use `ProtectedSocketFdSource`: a queued, already-protected socket is still consumed first (initial management socket, initial signal socket, and legacy management spare). When their queues are empty, a dial waits for one shell request. Relay always requests a fresh `purpose=relay` socket, never a legacy queued fd. None of these transports falls back to a bare socket. Relay and production STUN hostnames use the protected DNS stub when `SocketSupply` is installed; WireGuard UDP and ICE socket replenishment remain unchanged.

## Boundary

- Core emits one request per dial or DNS query: `socket_supply_poll() -> {"id":"<decimal u64>","kind":"tcp"|"udp","purpose":"management"|"signal"|"relay"|"dns"}`. No request is represented by `{"id":""}`. IDs are process-wide monotonic so a reply from an old session cannot fulfill a new session's request.
- ArkTS polls at 100 ms while its connector is active. For TCP it opens an unconnected socket with `mgmt_socket_open()`; for DNS it opens a fresh unbound UDP socket with `ice_socket_open()`. It calls `VpnConnection.protect(fd)` with the existing 5 s box, and replies through `socket_supply_reply(id, fd, "protected")` only on actual success and while the ability is alive. Otherwise it replies with `-1` and `"protect-failed"` or `"rejected"`. The development-only route-exclusion deviation is *not* accepted for demand requests. Before each DNS supply it refreshes the physical resolver list; an empty list rejects the request without opening a socket.
- A successful reply duplicates the original fd into an owned pending result. The shell closes its original fd with `socket_supply_close_fd(fd)` after the reply, including rejected, expired, and failed-protect paths. The dial duplicates the delivered descriptor before `connect` and drops the owned delivered copy. A stale ID never transfers an fd. `socket_supply_shutdown()` and connector stop cancel pending requests; the shell stops polling at teardown. Core times out unanswered requests after 8 s and fails that dial closed. Pending owned fds are dropped if the dial is cancelled.
- Core logs ID, purpose, socket kind, fd, result and elapsed milliseconds per reply; the shell logs the same alongside whether core accepted the reply. The DNS stub also logs hostname, server, fd, request ID, elapsed time and outcome. This is protocol observation, not evidence that `protect` succeeded on a device. Shell DNS resolution for the fixed management and signal connect addresses remains the existing startup flow; reconnects reuse those resolved addresses.

## Protected DNS

The initial shell snapshot reads IPv4 DNS resolvers only from a capability-confirmed physical default network. When VPN becomes the default, the shell rechecks that same physical network handle and its current DNS entries; it never pools DNS from other networks or uses VPN DNS entries. If the physical handle disappears or no IPv4 resolver remains, DNS fails closed. A query requests a fresh protected UDP fd for each server attempt, sets nonblocking mode, sends a minimal A query and waits up to 1.5 s for its response. ID, flags, question, answer record bounds and A/CNAME ownership are checked; mismatches and truncation cause retry on the next resolver. Query bytes cannot be sent on rejection, protect failure or supply timeout. Production relay and STUN use this path; explicitly injected host-test sources retain their original resolver. A numeric IPv4 literal needs no DNS socket. The socket supply itself has an 8 s per-request timeout.

Local fake-DNS tests cover valid answers, bad IDs, truncated records, timeout/server retry with fresh UDP fds, and rejection/no packet. Host tests cannot prove `VpnConnection.protect` device behavior, physical routing, or production DNS reachability. No device operation was performed.
