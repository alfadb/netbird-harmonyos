# On-demand protected socket supply (2026-09-27)

The production management and signal connectors use `ProtectedSocketFdSource`. A queued, already-protected socket is still consumed first (initial management socket, initial signal socket, and legacy management spare). When the queue is empty, a dial waits for one shell request. The transport never falls back to a bare socket. ICE replenishment, WireGuard UDP and relay dialing are unchanged.

## Boundary

- Core emits one request per dial: `socket_supply_poll() -> {"id":"<decimal u64>","kind":"tcp","purpose":"management"|"signal"}`. No request is represented by `{"id":""}`. IDs are process-wide monotonic so a reply from an old session cannot fulfill a new session's request. The enum also reserves `relay` and `dns` labels, with `dns` identified as UDP; these labels are not connected to a dial path or handled by this shell yet.
- ArkTS polls at 100 ms while its connector is active. For management/signal TCP, it opens an unconnected socket with `mgmt_socket_open()`, calls `VpnConnection.protect(fd)` with the existing 5 s box, and replies through `socket_supply_reply(id, fd, "protected")` only on actual success and while the ability is alive. Otherwise it replies with `-1` and `"protect-failed"` or `"rejected"`. The development-only route-exclusion deviation is *not* accepted for demand requests.
- A successful reply duplicates the original fd into an owned pending result. The shell closes its original fd with `socket_supply_close_fd(fd)` after the reply, including rejected, expired, and failed-protect paths. The dial duplicates the delivered descriptor before `connect` and drops the owned delivered copy. A stale ID never transfers an fd. `socket_supply_shutdown()` and connector stop cancel pending requests; the shell stops polling at teardown. Core times out unanswered requests after 8 s and fails that dial closed. Pending owned fds are dropped if the dial is cancelled.
- Core logs ID, purpose, socket kind, fd, result and elapsed milliseconds per reply; the shell logs the same alongside whether core accepted the reply. This is a protocol observation, not evidence that `protect` succeeded on a device. Shell DNS resolution for the fixed management and signal connect addresses remains the existing startup flow; DNS lookups are not transferred to native.

## Future consumers and limits

A relay consumer would need to attach a source to the same broker and route its connection attempts through the protected-socket connector; merely labeling a request `relay` does not protect relay traffic. DNS would additionally need a UDP socket acquisition and destination-aware resolver design in the shell, before any resolver traffic can use this bridge. No relay, DNS, WG or ICE behavior changes in this increment. Legacy pre-fed descriptors retain their prior borrowed-number lifetime; only on-demand descriptors use the owned-copy handoff. Host tests cannot prove `VpnConnection.protect` device behavior, VPN routing, or production signal/TLS recovery timing.
