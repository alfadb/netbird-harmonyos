# On-demand protected socket supply (2026-09-27)

The production management, signal and opt-in relay connectors use per-dial protected sockets. Management and signal use `ProtectedSocketFdSource`: a queued, already-protected socket is still consumed first (initial management socket, initial signal socket, and legacy management spare). When their queues are empty, a dial waits for one shell request. Relay always requests a fresh `purpose=relay` socket, never a legacy queued fd. None of these transports falls back to a bare socket. Relay and production STUN hostnames use the protected DNS stub when `SocketSupply` is installed; WireGuard UDP and ICE socket replenishment remain unchanged.

## Boundary

- Core emits one request per dial or DNS query: `socket_supply_poll() -> {"id":"<decimal u64>","kind":"tcp"|"udp","purpose":"management"|"signal"|"relay"|"dns"}`. No request is represented by `{"id":""}`. IDs are process-wide monotonic so a reply from an old session cannot fulfill a new session's request.
- ArkTS registers ONE callback (`socket_supply_subscribe(cb)`, released by `socket_supply_unsubscribe()`) and the core calls it from the enqueueing thread the moment a request enters the queue — the pushed form of the official Android client's platform callback (`client/android/client.go` hands the Go core `tunAdapter.ProtectSocket`; `client/net/protectsocket_android.go` calls it synchronously from the dial path; upstream has no host-side poll). The callback runs on the ArkTS thread, carries nothing, and services the queue until `socket_supply_poll()` answers `{"id":""}`; a request enqueued during that drain is picked up by the same loop. A slow 5 s `socket_supply_poll()` safety net remains for a wake the runtime could not deliver (the threadsafe call is nonblocking), which is also why the shell still drains once right after subscribing. For TCP it opens an unconnected socket with `mgmt_socket_open()`; for DNS it opens a fresh unbound UDP socket with `ice_socket_open()`. It calls `VpnConnection.protect(fd)` with the existing 5 s box, and replies through `socket_supply_reply(id, fd, "protected")` only on actual success and while the ability is alive. Otherwise it replies with `-1` and `"protect-failed"` or `"rejected"`. The development-only route-exclusion deviation is *not* accepted for demand requests. Before each DNS supply it refreshes the physical resolver list; an empty list rejects the request without opening a socket.
- A successful reply duplicates the original fd into an owned pending result. The shell closes its original fd with `socket_supply_close_fd(fd)` after the reply, including rejected, expired, and failed-protect paths. The dial retains that owned descriptor through `connect` (and duplicates it for the `EISCONN` adoption path). A stale ID never transfers an fd. `socket_supply_shutdown()` and connector stop cancel pending requests; the shell stops polling at teardown. Core times out unanswered requests after 8 s and fails that dial closed. Pending owned fds are dropped if the dial is cancelled.
- Core logs ID, purpose, socket kind, fd, result and elapsed milliseconds per reply; the shell logs the same alongside whether core accepted the reply. The DNS stub also logs hostname, server, fd, request ID, elapsed time and outcome. This is protocol observation, not evidence that `protect` succeeded on a device. Recovery management and signal hostnames use the same protected DNS stub via nonblocking `connector_protected_dns_start` / `connector_protected_dns_poll`; ArkTS never blocks its event loop waiting for a socket-supply request.

## Physical-network recovery

- ArkTS observes `netAvailable`, `netLost`, and `netCapabilitiesChange` while the connector runs. Loss of the selected network immediately calls `connector_physical_network_changed("")`, canceling pending requests and draining queued management/signal/ICE descriptors before any DNS lookup or replacement socket can be attempted. Availability/capability callbacks are coalesced for 250 ms; selection uses the capability-confirmed physical default, or a single unambiguous physical network while the VPN is the platform default. Ambiguous candidates do not trigger a replacement. Changes during startup are deferred until the VPN connection and connector are ready. The observer is unregistered on teardown.
- On recovery, the shell reads IPv4 resolvers for the selected physical handle and publishes them to core before starting management DNS. Management and signal names are resolved asynchronously by the protected DNS stub; unresolved names leave the old queues empty and do not start any unprotected dial. The shell opens and protects a fresh ephemeral-bound WG UDP socket, feeds it to the live device, and closes its original immediately after the feed returns; core duplicates it before returning, and a failed replacement retains the previous live socket. Core restarts ICE and signal, stops relay, updates the management dial address, and wakes the management worker. The shell supplies newly protected ICE, signal, and management fds. Subsequent relay dials request new protected sockets; relay resumes from the next Sync map.
- In-flight demand requests from a previous network generation cannot supply a stale fd after recovery. The shell declines demand requests during a dirty transition, and core rejects late replies for canceled request IDs. A DNS request uses only the selected physical network handle. Startup and transport reconnect failures remain fail-closed; they are retried on later network events or connector reconnects, not on bare sockets.
- Host tests verify a live WG feed replacement with byte-exact bidirectional encrypted payloads, invalid replacement preserving the previous path, cancellation of pending supplies, and protected DNS updates. On a device, verify Wi-Fi→cellular and cellular→Wi-Fi while passing traffic; loss then restore with no VPN/default-network DNS substitution; actual `protect(fd)` results for each new WG, ICE, management, signal, relay, and DNS socket; fresh source addresses, management/Signal re-registration, relay reestablishment, and ICE-selected endpoint changes. Check shell originals close after core accepts their owned duplicates (or on failure), while the original TUN remains platform-owned; observe both failure/retry and successful resume in hilog. Host loopback cannot establish radio routing, platform VPN protection, real DNS reachability, or whether relay Sync arrives after a reconnect.

## Protected DNS

The initial shell snapshot reads IPv4 DNS resolvers only from a capability-confirmed physical default network. When VPN becomes the default, the shell rechecks that same physical network handle and its current DNS entries; it never pools DNS from other networks or uses VPN DNS entries. If the physical handle disappears or no IPv4 resolver remains, DNS fails closed. A query requests a fresh protected UDP fd for each server attempt, sets nonblocking mode, sends a minimal A query and waits up to 1.5 s for its response. ID, flags, question, answer record bounds and A/CNAME ownership are checked; mismatches and truncation cause retry on the next resolver. Query bytes cannot be sent on rejection, protect failure or supply timeout. Production ICE/STUN hostnames are resolved asynchronously through protected DNS before gather; cache-only lookup inside the ICE lock never blocks waiting for ArkTS socket supply. On OHOS no system `getaddrinfo` fallback is permitted for nonliteral STUN hosts. A numeric IPv4 literal needs no DNS socket. The socket supply itself has an 8 s per-request timeout. The route-exclusion protect bypass is rejected before connector startup, as is the conflicting combination of disabled endpoint exclusions with diagnostic capture routing.

Local fake-DNS tests cover valid answers, bad IDs, truncated records, timeout/server retry with fresh UDP fds, and rejection/no packet. Host tests cannot prove `VpnConnection.protect` device behavior, physical routing, or production DNS reachability. No device operation was performed.
