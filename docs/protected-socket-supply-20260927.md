# On-demand protected socket supply (2026-09-27)

The production management, signal and opt-in relay connectors use per-dial protected sockets. Management and signal use `ProtectedSocketFdSource`: a queued, already-protected socket is still consumed first (initial management socket, initial signal socket, and legacy management spare). When their queues are empty, a dial waits for one shell request. Relay always requests a fresh `purpose=relay` socket, never a legacy queued fd. None of these transports falls back to a bare socket. ICE replenishment, WireGuard UDP and DNS are unchanged.

## Boundary

- Core emits one request per dial: `socket_supply_poll() -> {"id":"<decimal u64>","kind":"tcp","purpose":"management"|"signal"|"relay"}`. No request is represented by `{"id":""}`. IDs are process-wide monotonic so a reply from an old session cannot fulfill a new session's request. The enum also reserves `dns` as UDP, but DNS is not connected to this dial path or handled by this shell yet.
- ArkTS polls at 100 ms while its connector is active. For management/signal/relay TCP, it opens an unconnected socket with `mgmt_socket_open()`, calls `VpnConnection.protect(fd)` with the existing 5 s box, and replies through `socket_supply_reply(id, fd, "protected")` only on actual success and while the ability is alive. Otherwise it replies with `-1` and `"protect-failed"` or `"rejected"`. The development-only route-exclusion deviation is *not* accepted for demand requests.
- A successful reply duplicates the original fd into an owned pending result. The shell closes its original fd with `socket_supply_close_fd(fd)` after the reply, including rejected, expired, and failed-protect paths. The dial duplicates the delivered descriptor before `connect` and drops the owned delivered copy. A stale ID never transfers an fd. `socket_supply_shutdown()` and connector stop cancel pending requests; the shell stops polling at teardown. Core times out unanswered requests after 8 s and fails that dial closed. Pending owned fds are dropped if the dial is cancelled.
- Core logs ID, purpose, socket kind, fd, result and elapsed milliseconds per reply; the shell logs the same alongside whether core accepted the reply. This covers relay attempts and their protect outcomes too; it is protocol observation, not evidence that `protect` succeeded on a device. Shell DNS resolution for the fixed management and signal connect addresses remains the existing startup flow. Relay hostname resolution still uses the existing platform resolver (`lookup_host`) before connecting on the protected fd; moving DNS queries onto protected sockets is a separate task.

## Future consumers and limits

DNS needs UDP socket acquisition and a destination-aware resolver design in the shell before resolver traffic can use this bridge. No DNS, WG or ICE behavior changes in this increment. Legacy pre-fed descriptors retain their prior borrowed-number lifetime; only on-demand descriptors use the owned-copy handoff. The explicitly unprotected management startup has no broker, so its relay dialer fails closed even when relay is enabled. Host tests cannot prove `VpnConnection.protect` device behavior, VPN routing, relay hostname DNS routing, or production signal/TLS recovery timing.
