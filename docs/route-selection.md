# 路由选择使用说明（v0.0.12）

本文说明 HarmonyOS 客户端 v0.0.12 的「设置 → 路由选择」功能。相比 0.0.11，开关不再有「保存 / 保存并重新连接」：改动**立即写入并通知当前连接**。文末是开发者要点、v1 范围限制和当前验证状态。

## 一、功能是什么

- 管理端（NetBird）下发「网络路由」（network routes），例如让 `192.168.50.0/24` 经某个 peer 转发。
- 客户端按 **NetID**（管理端给逻辑网络的标识）分组展示，用户逐个开关，不需要保存。
- 同一个 NetID 可能有多个 **HA 候选**（高可用候选，同网段、不同 peer/metric），开关按 NetID 生效：该网络的所有候选一起变化。实测样例：`HostInternal` / `192.168.50.0/24`，NetHostDebian（metric 100）与 RPi（metric 200）。
- 关闭某个网络后，该网络不进入 VPN 的路由表（不会被本机经隧道转发）。
- **默认全开**：没有任何已保存偏好时，当前和以后新出现的网络全部启用。

## 二、怎么用（用户）

1. 打开「设置 → 路由选择」：每行是 NetID、网段（多个用「、」分隔）、节点数（该 NetID 的 HA 候选数）和开关；显式 `0.0.0.0/0` 出口路由单独放在「出口节点」分区。
2. **开关和「全部启用 / 全部停用」都即刻生效**：先原子写入选择，再通知当前连接重新应用。没有「保存」「放弃更改」按钮；**返回页面不会丢弃改动**——改动在拨动那一刻就已经落盘。
3. 连续快速拨动是**串行写入、最新者生效**：同一时刻只有一次写入在飞，更晚的意图覆盖排队中的旧意图；旧写入既不会覆盖新意图，也不会为已被取代的状态发通知。
4. 离线或连接未就绪时：选择照常保存，**在下次连接时生效**，当前连接不动。
5. **「全部停用」是全局动作**：当前所有网络以及**以后新增的网络**都默认停用（可再单独打开某些网络作为例外）；「全部启用」恢复全开。
6. 页面按结果如实显示：正在应用 / 已生效 / 失败（附原因）；只存了偏好、还没交给系统时显示「将在下次连接时生效」。

## 三、开发者要点

- **只有一个过滤点**：core 在应用 NetworkMap 时只调用一次 `filter_selected`；之后 shell 快照、`net_routes_all`、WG managed routes、`host.apply` 看到的是同一份过滤后的路由列表。
- **peer 的基础 `allowed_ips` 不受影响**：选择只作用于管理路由；对端 overlay 的 `/32` 等地址即使「全部停用」也保留。
- **界面读的是未过滤的离线缓存** `netbird-routes.json`，展示管理端 advertised 的全部行（含已关闭的）；真正生效由 core 过滤。`available:true` + `networks:[]` 表示「已连接但确实没有路由」，不是「没有目录」。
- **全部停用不会退回 `0.0.0.0/0`**：显式快照生效路由为空时，平台 VpnConfig 不回填模板默认路由，只保留基础的非默认条目（隧道 overlay 地址/网段模板）和基础排除项。
- **本地文件（都在 filesDir）**：
  - `netbird-route-selection.json`：v1 偏好，按 management URL 分作用域，明文公共配置（不含 token/私钥，凭据仍单独存放）。文件缺失或属于另一个管理 URL = 无偏好（默认全开）；**文件损坏或版本不符是稳定错误，不静默回默认，读取也不重写该文件**（否则会覆盖用户设置并在下次保存时销毁证据）。
  - `netbird-route-apply-request.json`：界面 → VPE 的**通知**。只有不透明的请求 id、management URL 和写入时间；**不含选择副本、不绑定会话**——VPE 自己按当前 management URL 读最新偏好。原子写入；**处理完也不删除**（同一 id 重复读到是空操作），应用期间到来的新 id 由后续轮次接着处理。
  - `netbird-route-apply-result.json`：VPE → 界面的结果。带上被回答的请求 id、状态 `applying` / `applied` / `failed`、方式、失败原因、NetID 列表和时间。**只有**「重建完成并确认」或「原生证明系统侧本来就不需要改动」才等于 `applied`；只存了偏好、没交给系统的结果**不算**已生效，界面按「下次连接生效」显示。
- **SDK API 26 不能就地改路由**：`@ohos.net.vpnExtension.d.ts` 里 `VpnConnection` 只有 `create(config)` 和 `destroy()`，没有更新路由的接口。因此应用新选择要按新配置**销毁并重建本机 VPN 连接**；这个过程**不重启 NetBird 本身**——management / WG / ICE 保持已经建立成功的那条会话不变（不重新登录、不重建隧道）。
- **用户主动改动不占用自动重连的「3 次 / 30 秒」预算**（这条区分已在宿主机原生测试中验证）；自动路径的限额保持不变。
- **写失败就不改连接**：偏好写入失败时既不通知也不停止/连接，连接状态保持原样；通知写入失败只提示「已保存，将在下次连接生效」，绝不显示已生效。
- **界面只认自己最新写出的请求 id**：id 不匹配（历史结果、别处的结果）一律不显示为已生效；**管理端目录里的 `enabled` 不是已生效的证据**；重新打开页面不会认领历史请求 id，所以历史结果不会被当成「已生效」。

## 四、v1 范围与已知限制

- v1 只实现**显式 IPv4 路由**，包含显式 `0.0.0.0/0` exit 路由（同样按 NetID 开关，界面单独分区）。
- **不是**官方 Windows v0.80 的完整 exit-node 语义：没有 exit 自动跳过（autoSkip）、没有 exit 互斥、没有 DNS、没有 IPv6 支持。
- 若剩余生效路由里仍有 `0.0.0.0/0`（或更宽前缀），被关闭的子网**仍可能经该 exit 走出去**（正常的剩余最长前缀匹配）。因此「关闭管理网络」**不承诺**强制改走物理链路。
- 应用新选择要销毁并重建本机 VPN 连接：**切换瞬间可能短暂中断数据**。中断时长**尚未测量**，因此**不承诺零中断**。
- **旧限制已消除（宿主机验证）**：过去初始生效路由集为空时，shell 回执（ACK）也是空集，之后服务端新增路由可能需要重连才能生效；新路径不再如此。真机层面仍未验证，见第五节。
- 不修改管理服务器。
